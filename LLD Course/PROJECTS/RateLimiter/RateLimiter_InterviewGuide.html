Understanding the problem in depth — first

What is a Rate Limiter, really? It's a gatekeeper that sits in front of a resource (API, login endpoint, SMS service) and decides: "Has this client made too many requests recently? If yes, reject. If no, let it through and record this request."
Why this question is popular for SDE-1: It tests two things at once — (1) can you design clean OOP classes, and (2) do you understand a real algorithm (token bucket / sliding window). Most candidates can do one but not both. Knowing both makes you stand out.

The 4 classic algorithms — know all 4 names, pick ONE to implement fully:

Token Bucket Pick this one
Bucket holds tokens (capacity). Tokens refill at fixed rate. Each request consumes 1 token. No tokens = reject. Allows bursts up to capacity.
Fixed Window Counter Mention
Count requests in a fixed time window (e.g. per minute). Reset counter when window ends. Simple but allows 2x burst at window boundaries.
Sliding Window Log Mention
Store timestamp of every request. Count requests in last N seconds by removing old timestamps. Accurate but memory-heavy.
Leaky Bucket Mention
Like token bucket but processes requests at a fixed output rate (queue-based). Smooths bursts instead of allowing them.
Why Token Bucket is the safest pick for interviews: It's the algorithm used by AWS, Stripe, and most real APIs. It's easy to explain with an analogy ("imagine a bucket that refills with tokens over time"), and the code is short — about 15 lines of core logic. This is what we'll build.

Phase 2 — Identify Entities & Quick Diagram

10 – 20 min
Rate limiter has FEWER entities than typical LLD — but more interfaces. Don't think "what nouns exist in the real world" (there's no physical object here). Instead think "what VARIES, and what STAYS THE SAME". The thing that varies (the algorithm) becomes an interface.
Step 1 — Identify the "varies vs fixed" split (2 min, say out loud)
Say: "The core thing that can vary is the algorithm — token bucket today, sliding window tomorrow. So I'll define a RateLimiterAlgorithm interface with one method: allowRequest(). Everything else — the manager that maps users to their bucket — stays fixed."
Step 2 — List the classes (2 min)
— RateLimiterAlgorithm (interface) — the Strategy
— TokenBucketRateLimiter — implements the interface
— RateLimiterConfig — holds capacity + refill rate (just data)
— RateLimiter — the main class, holds a Map<clientId, Algorithm>
— RateLimiterFactory — creates the right algorithm based on config

Don't draw boxes-with-fields like a normal ER diagram. For algorithm-heavy LLDs, draw a tiny component diagram: 3 boxes max, showing the flow Client → RateLimiter → Algorithm (per client). Say: "I'll keep this very lightweight — just the call flow."

Phase 3 — The Complete Code

20 – 55 min
Say this before typing: "I'll start with the algorithm interface — this is the heart of the Strategy pattern. Everything else plugs into it."
RateLimiterAlgorithm.java
Strategy Pattern — the contractISP + DIP
// ── Design Pattern: STRATEGY (this interface IS the strategy contract) ──
// Any algorithm — Token Bucket, Sliding Window, Leaky Bucket — implements this.
// ── SOLID: Interface Segregation ──────────────────────────────────────────
// Just ONE method. No implementation is forced to support things it doesn't need.
// ── SOLID: Dependency Inversion ───────────────────────────────────────────
// RateLimiter (high-level) depends on THIS abstraction, not on TokenBucket directly.

public interface RateLimiterAlgorithm {
    // Returns true if the request is allowed right now, false if rate-limited
    boolean allowRequest();
}
RateLimiterConfig.java
SRP — pure data holder
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Holds configuration ONLY. No logic. Decouples "what the limits are"
// from "how the limiting algorithm works".
// Using a builder-less simple class here for brevity — in production,
// you'd add a Builder pattern if there were many optional fields.

public class RateLimiterConfig {
    private final long capacity;          // max tokens (burst size)
    private final long refillRatePerSec;  // tokens added per second

    public RateLimiterConfig(long capacity, long refillRatePerSec) {
        this.capacity         = capacity;
        this.refillRatePerSec = refillRatePerSec;
    }

    public long getCapacity()         { return capacity; }
    public long getRefillRatePerSec() { return refillRatePerSec; }
}
TokenBucketRateLimiter.java
Strategy — concrete implementationSRP + OCP
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// This class does ONE thing: implement the token-bucket algorithm for ONE client.
// ── SOLID: Open/Closed ────────────────────────────────────────────────────
// To add SlidingWindowRateLimiter later — new class, implements same interface.
// Zero changes needed here or in RateLimiter.
//
// ── THE ALGORITHM (explain this out loud while writing) ───────────────────
// Think of a bucket that holds up to `capacity` tokens.
// Tokens refill continuously at `refillRatePerSec` tokens/second.
// Each request consumes 1 token. If bucket is empty → reject.
// "Lazy refill": instead of a background thread adding tokens every tick,
// we calculate elapsed time on EACH request and refill accordingly.
// This avoids needing a scheduler/thread — much simpler & interview-friendly.

public class TokenBucketRateLimiter implements RateLimiterAlgorithm {

    private final long capacity;
    private final long refillRatePerSec;
    private double currentTokens;            // double — allows fractional refills
    private long lastRefillTimestamp;        // epoch millis of last refill calc

    public TokenBucketRateLimiter(RateLimiterConfig config) {
        this.capacity         = config.getCapacity();
        this.refillRatePerSec = config.getRefillRatePerSec();
        this.currentTokens   = capacity;        // start full — generous to new clients
        this.lastRefillTimestamp = System.currentTimeMillis();
    }

    // 'synchronized' — multiple threads could call this for the same client
    // at the same time (e.g. parallel requests). Must be thread-safe.
    @Override
    public synchronized boolean allowRequest() {
        refill();                              // step 1: top up tokens based on elapsed time

        if (currentTokens >= 1) {           // step 2: do we have a token to spend?
            currentTokens -= 1;                // step 3: consume it
            return true;
        }
        return false;                       // bucket empty → reject
    }

    // Adds tokens proportional to elapsed time since last refill.
    // Capped at `capacity` — bucket can't overflow.
    private void refill() {
        long now = System.currentTimeMillis();
        double elapsedSeconds = (now - lastRefillTimestamp) / 1000.0;

        double tokensToAdd = elapsedSeconds * refillRatePerSec;
        if (tokensToAdd > 0) {
            currentTokens = Math.min(capacity, currentTokens + tokensToAdd);
            lastRefillTimestamp = now;
        }
    }
}
RateLimiterType.java + RateLimiterFactory.java
Factory PatternOCP
// ── Design Pattern: FACTORY ───────────────────────────────────────────────
// Caller says WHAT algorithm they want (an enum), not HOW to build it.
// ── SOLID: Open/Closed ────────────────────────────────────────────────────
// Adding SlidingWindow: add enum value + one case. RateLimiter class untouched.

public enum RateLimiterType {
    TOKEN_BUCKET,
    SLIDING_WINDOW   // not implemented here, but enum shows extensibility
}

public class RateLimiterFactory {
    public static RateLimiterAlgorithm create(RateLimiterType type, RateLimiterConfig config) {
        switch (type) {
            case TOKEN_BUCKET:
                return new TokenBucketRateLimiter(config);
            // case SLIDING_WINDOW: return new SlidingWindowRateLimiter(config);
            default:
                throw new IllegalArgumentException("Unsupported type: " + type);
        }
    }
}
RateLimiter.java
Singleton + Factory usageSRP + DIP
import java.util.*;
import java.util.concurrent.*;

// ── Design Pattern: SINGLETON ─────────────────────────────────────────────
// Like ParkingLot, there's ONE global rate limiter registry per application.
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// This class does ONE thing: map a clientId to ITS OWN algorithm instance,
// and delegate the actual decision to that instance.
// ── SOLID: Dependency Inversion ───────────────────────────────────────────
// Depends on RateLimiterAlgorithm (interface) — doesn't know it's TokenBucket.

public class RateLimiter {

    // ── Singleton: standard pattern, same as ParkingLot ──────────────
    private static volatile RateLimiter instance;

    private final RateLimiterType type;
    private final RateLimiterConfig config;

    // ConcurrentHashMap — multiple threads create/read entries for
    // DIFFERENT clients simultaneously. Must be thread-safe at the map level too.
    private final Map<String, RateLimiterAlgorithm> clientLimiters;

    private RateLimiter(RateLimiterType type, RateLimiterConfig config) {
        this.type   = type;
        this.config = config;
        this.clientLimiters = new ConcurrentHashMap<>();
    }

    public static RateLimiter getInstance(RateLimiterType type, RateLimiterConfig config) {
        if (instance == null) {
            synchronized (RateLimiter.class) {
                if (instance == null) {
                    instance = new RateLimiter(type, config);
                }
            }
        }
        return instance;
    }

    // ── THE MAIN METHOD ─────────────────────────────────────────────
    // 1. Find or create a per-client algorithm instance (lazy creation)
    // 2. Delegate the decision to it
    // computeIfAbsent = atomic "get or create" — avoids race conditions
    // where two threads both create a limiter for a NEW client.
    public boolean isAllowed(String clientId) {
        RateLimiterAlgorithm limiter = clientLimiters.computeIfAbsent(
            clientId,
            id -> RateLimiterFactory.create(type, config)
        );
        return limiter.allowRequest();
    }
}
Main.java
Always demo — prove burst + throttle
public class Main {
    public static void main(String[] args) throws InterruptedException {

        // 5 requests capacity, refilling at 5 tokens/sec → "5 req/sec, bursts up to 5"
        RateLimiterConfig config = new RateLimiterConfig(5, 5);
        RateLimiter limiter = RateLimiter.getInstance(RateLimiterType.TOKEN_BUCKET, config);

        String user = "user-123";

        // Burst of 7 requests instantly — first 5 should pass, last 2 rejected
        for (int i = 1; i <= 7; i++) {
            boolean allowed = limiter.isAllowed(user);
            System.out.printf("Request %d → %s%n", i, allowed ? "ALLOWED" : "REJECTED");
        }

        System.out.println("\nWaiting 1 second for refill...\n");
        Thread.sleep(1000);

        // After 1 sec, ~5 tokens refilled → next requests should pass again
        for (int i = 8; i <= 10; i++) {
            boolean allowed = limiter.isAllowed(user);
            System.out.printf("Request %d → %s%n", i, allowed ? "ALLOWED" : "REJECTED");
        }

        // Different user — gets its OWN bucket, unaffected by user-123's usage
        System.out.println("\nDifferent user:");
        System.out.println("Request 1 → " + (limiter.isAllowed("user-456") ? "ALLOWED" : "REJECTED"));
    }
}

SOLID Principles — where exactly in the code

How to bring this up: Rate Limiter is actually the BEST problem to demonstrate SOLID because the interface-driven design makes every principle visible. Call them out as you write each class.
S
Single Responsibility
Every class has exactly one reason to change.
TokenBucketRateLimiter — only the algorithm math. RateLimiterConfig — only holds numbers. RateLimiter — only routes clientId to its bucket.
O
Open / Closed
Open for extension, closed for modification.
Add SlidingWindowRateLimiter → new class implementing RateLimiterAlgorithm + one factory case. Zero changes to RateLimiter or existing algorithms.
L
Liskov Substitution
Any implementation can replace another without breaking callers.
RateLimiter calls limiter.allowRequest() — works identically whether limiter is TokenBucketRateLimiter or any future SlidingWindowRateLimiter.
I
Interface Segregation
Don't force implementations to support unused methods.
RateLimiterAlgorithm has exactly ONE method — allowRequest(). No bloated interface forcing every algorithm to implement getRemainingTokens(), reset(), etc. unless truly needed.
D
Dependency Inversion
High-level modules depend on abstractions, not concrete classes.
RateLimiter (high-level) holds Map<String, RateLimiterAlgorithm> — the abstraction — never references TokenBucketRateLimiter directly. The Factory is the only place that knows concrete types. This is THE textbook DIP example.
P

Design Patterns — what's used and why

1
Strategy Pattern (the core pattern of this problem)
The rate-limiting algorithm is a behavior that can vary independently of the rest of the system. By defining RateLimiterAlgorithm as an interface, we can swap Token Bucket for Sliding Window at runtime, per client, or per endpoint — without touching RateLimiter's code at all. This is the single most important design decision in this problem, and naming it explicitly is what separates SDE-1 from SDE-2 answers.
Used in: RateLimiterAlgorithm interface + TokenBucketRateLimiter implementation
2
Factory Pattern
RateLimiter shouldn't know HOW to construct a TokenBucketRateLimiter (what constructor args it needs, etc). The Factory encapsulates that knowledge. If TokenBucketRateLimiter's constructor changes, only the factory changes — RateLimiter is untouched.
Used in: RateLimiterFactory.create()
3
Singleton Pattern
There's one global rate-limiting service per application — similar reasoning to ParkingLot. All requests across the app go through the same registry of per-client buckets. Double-checked locking with volatile makes it thread-safe without locking on every read.
Used in: RateLimiter.getInstance()
4
Decorator Pattern (extension — mention if asked about logging/metrics)
If the interviewer asks "how would you add logging or metrics without modifying TokenBucketRateLimiter?" — say: "I'd wrap it in a LoggingRateLimiterDecorator implements RateLimiterAlgorithm that logs before/after delegating to the real algorithm. This is the Decorator pattern — adding behavior without modifying the original class (OCP again)."
Extension point: LoggingRateLimiterDecorator wraps RateLimiterAlgorithm
LoggingRateLimiterDecorator.java — bonus answer
Decorator Pattern
// ── Design Pattern: DECORATOR ─────────────────────────────────────────────
// Wraps any RateLimiterAlgorithm and adds logging — without modifying it.
// Implements the SAME interface, so RateLimiter doesn't know the difference.

public class LoggingRateLimiterDecorator implements RateLimiterAlgorithm {
    private final RateLimiterAlgorithm delegate;
    private final String clientId;

    public LoggingRateLimiterDecorator(RateLimiterAlgorithm delegate, String clientId) {
        this.delegate = delegate;
        this.clientId = clientId;
    }

    @Override
    public boolean allowRequest() {
        boolean result = delegate.allowRequest();
        System.out.printf("[METRIC] client=%s allowed=%b%n", clientId, result);
        return result;
    }
}

Interview Tips — what separates good from great

Things to DO
✓Name the algorithm out loud before coding (Token Bucket)
✓Define the interface FIRST — show Strategy thinking upfront
✓Use synchronized + explain WHY (concurrent requests)
✓Use lazy "refill on read" — avoids needing a background thread
✓Demo with a burst test — prove limit AND refill both work
✓Mention distributed extension (Redis) without over-engineering
Things to AVOID
✗Hardcoding TokenBucketRateLimiter everywhere (no interface)
✗Using a background Timer/Thread to refill tokens (overcomplicated)
✗Forgetting thread-safety (multiple requests = race conditions)
✗Using a single shared bucket for ALL users (no per-client isolation)
✗Jumping into Redis/distributed design unprompted (scope creep)
✗Not explaining the refill math — interviewer can't follow silently
Bonus questions to prepare for:
"How would you make this distributed?" → Replace the HashMap with Redis (INCR + TTL or Lua script for atomicity). The RateLimiterAlgorithm interface stays the same — only the storage backing it changes. This is exactly why we abstracted it.
"What if two threads call isAllowed() for the same user at the same instant?" → synchronized on allowRequest() ensures only one thread mutates currentTokens at a time. computeIfAbsent on ConcurrentHashMap prevents duplicate bucket creation.
"How would you support different limits per endpoint?" → Key the map by (clientId + endpoint) instead of just clientId, and pass different RateLimiterConfig per endpoint type.
"Difference between Token Bucket and Leaky Bucket?" → Token Bucket allows bursts up to capacity; Leaky Bucket processes at a constant rate via a queue, smoothing bursts entirely.
"How would you clean up old client entries (memory leak)?" → Add a scheduled eviction — remove entries where lastRefillTimestamp is older than some TTL (e.g. 1 hour of inactivity).
