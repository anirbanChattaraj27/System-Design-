Understanding the problem in depth — first

What is a Logging Framework, really? It's a system where application code calls logger.info("message") or logger.error("message"), and the framework decides: (1) is this message important enough to record right now (based on configured level), and (2) where should it go — console, file, database, all of them?
Why this question is popular for SDE-1: Unlike Parking Lot, there's almost ZERO "real world" entity modeling — it's 90% design patterns. This is the interviewer's favourite way to test "do you actually know Strategy, Singleton, Factory, Chain of Responsibility, or do you just say the names?"

The 2 core "axes of variation" — identify these first, everything else follows:

WHERE logs go Appender — Strategy
Console, File, Database, Remote server. Each is a different "sink". Must be pluggable and combinable (log to console AND file at once).
WHICH logs get through LogLevel filtering
DEBUG < INFO < WARN < ERROR < FATAL. If logger's configured level is WARN, then INFO and DEBUG messages are silently dropped.
HOW logs look Formatter — Strategy
Plain text "[INFO] 2026-06-13 message" vs JSON {"level":"INFO",...}. Optional but shows depth if mentioned.
Level routing chain Chain of Responsibility
Classic Log4j-style: a chain of level-handlers, each deciding to handle or pass along. Mention as "textbook alternative design" — interviewers love when you know this exists even if you don't implement it.
The approach we'll build: A simple, clean design — Logger (Singleton) holds a minimum log level + a list of LogAppender (Strategy). When log(level, msg) is called, check the level, then loop through all appenders and write. This is simpler than full Chain of Responsibility but covers 90% of what's asked — and we'll mention CoR as the "more advanced" alternative when asked.

Phase 2 — Identify Entities & Quick Diagram

10 – 20 min
Same mindset as Rate Limiter: ask "what varies vs what's fixed". Two things vary independently here — WHERE logs go (Appender) and HOW levels are ordered/filtered (LogLevel). Both become small, focused types.
Step 1 — Identify the "varies vs fixed" split (2 min, say out loud)
Say: "The destination of a log varies — console vs file vs future remote — so that's a LogAppender interface (Strategy). The level ordering is fixed but needs comparison logic, so that's an enum with ordinal-based severity. The Logger itself is the fixed orchestrator — one per app, so Singleton."
Step 2 — List the classes (2 min)
— LogLevel (enum) — DEBUG, INFO, WARN, ERROR, FATAL with ordinal severity
— LogMessage — data holder (level, text, timestamp)
— LogAppender (interface) — the Strategy: append(LogMessage)
— ConsoleAppender, FileAppender — implementations
— LogFormatter (interface) — formats a LogMessage into a String
— Logger — Singleton; holds minLevel + List<LogAppender> + formatter

Same "component diagram" approach as Rate Limiter — not an ER diagram with foreign keys, but a flow diagram: Caller → Logger → [list of Appenders], with LogLevel as a filter gate before the fan-out. Say: "I'll sketch the flow, not entity relationships — this problem doesn't have a database model."

Phase 3 — The Complete Code

20 – 55 min
Say this before typing: "I'll start with LogLevel — getting the severity ordering right up front avoids bugs later when I write the filtering check in Logger."
LogLevel.java
Foundation — ordered enum
// ── Why ORDER matters here ────────────────────────────────────────────────
// Java enums have a built-in ordinal() based on declaration order.
// DEBUG=0, INFO=1, WARN=2, ERROR=3, FATAL=4 — declared low-to-high severity.
// This lets us write: if (messageLevel.ordinal() >= minLevel.ordinal())
// No need for a separate "severity" field — ordinal() gives it for free.

public enum LogLevel {
    DEBUG,  // 0 — most verbose, dev-only details
    INFO,   // 1 — general informational messages
    WARN,   // 2 — something unexpected, but not broken
    ERROR,  // 3 — something failed
    FATAL   // 4 — application cannot continue
}
LogMessage.java
SRP — pure data holder
import java.time.LocalDateTime;

// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Just carries data between Logger and Appenders/Formatter. No behavior.
// Immutable (all fields final) — once created, a log record never changes.

public class LogMessage {
    private final LogLevel level;
    private final String text;
    private final LocalDateTime timestamp;

    public LogMessage(LogLevel level, String text) {
        this.level     = level;
        this.text      = text;
        this.timestamp = LocalDateTime.now();
    }

    public LogLevel getLevel()     { return level; }
    public String getText()        { return text; }
    public LocalDateTime getTimestamp() { return timestamp; }
}
LogFormatter.java + SimpleLogFormatter.java
StrategySRP + OCP
// ── Design Pattern: STRATEGY (formatting) ─────────────────────────────────
// HOW a message looks (plain text vs JSON) is independent of WHERE it goes.
// ── SOLID: Open/Closed ────────────────────────────────────────────────────
// Add JsonLogFormatter later → new class implementing this interface.
// Logger and Appenders need ZERO changes.

public interface LogFormatter {
    String format(LogMessage message);
}

// Default implementation — "[LEVEL] timestamp: message"
public class SimpleLogFormatter implements LogFormatter {
    @Override
    public String format(LogMessage message) {
        return String.format("[%s] %s: %s",
            message.getLevel(),
            message.getTimestamp(),
            message.getText());
    }
}
LogAppender.java + ConsoleAppender.java + FileAppender.java
Strategy — the core patternSRP + ISP + OCP
// ── Design Pattern: STRATEGY (the heart of this problem) ──────────────────
// "Where does this log go?" varies — console, file, remote server, DB...
// Each destination implements the same one-method contract.
// ── SOLID: Interface Segregation ──────────────────────────────────────────
// Just ONE method: append(). No appender is forced to implement unrelated stuff.
// ── SOLID: Open/Closed ─────────────────────────────────────────────────────
// Add DatabaseAppender or RemoteAppender → new class implementing this.
// Logger code (the orchestrator) doesn't change AT ALL.

public interface LogAppender {
    void append(String formattedMessage);
}

// ── SOLID: Single Responsibility ──────────────────────────────────────────
// ConsoleAppender knows ONLY how to print to System.out. Nothing else.
public class ConsoleAppender implements LogAppender {
    @Override
    public void append(String formattedMessage) {
        System.out.println(formattedMessage);
    }
}

// ── SOLID: Single Responsibility ──────────────────────────────────────────
// FileAppender knows ONLY how to write to a file. Opens in append mode
// so each log call adds a new line without overwriting previous logs.
import java.io.*;

public class FileAppender implements LogAppender {
    private final String filePath;

    public FileAppender(String filePath) {
        this.filePath = filePath;
    }

    @Override
    public void append(String formattedMessage) {
        // try-with-resources: auto-closes the writer even on exception
        try (FileWriter fw = new FileWriter(filePath, true);  // true = append mode
             PrintWriter pw = new PrintWriter(fw)) {
            pw.println(formattedMessage);
        } catch (IOException e) {
            System.err.println("Failed to write log to file: " + e.getMessage());
        }
    }
}
Logger.java
Singleton + Strategy usageSRP + DIP
import java.util.*;
import java.util.concurrent.*;

// ── Design Pattern: SINGLETON ─────────────────────────────────────────────
// One global logger configuration shared across the entire application.
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Logger's ONE job: (1) check level, (2) format, (3) fan out to appenders.
// It does NOT know HOW to write to console/file — that's delegated.
// ── SOLID: Dependency Inversion ───────────────────────────────────────────
// Logger depends on LogAppender + LogFormatter interfaces — never on
// ConsoleAppender or FileAppender directly.

public class Logger {

    private static volatile Logger instance;

    private LogLevel minLevel;
    private final List<LogAppender> appenders;
    private LogFormatter formatter;

    private Logger() {
        this.minLevel  = LogLevel.INFO;            // sensible default
        this.appenders = new CopyOnWriteArrayList<>(); // thread-safe iteration + add
        this.formatter = new SimpleLogFormatter();   // default formatter
    }

    public static Logger getInstance() {
        if (instance == null) {
            synchronized (Logger.class) {
                if (instance == null) {
                    instance = new Logger();
                }
            }
        }
        return instance;
    }

    // ── Configuration methods — call once at app startup ────────────
    public void setMinLevel(LogLevel level)     { this.minLevel = level; }
    public void setFormatter(LogFormatter f)    { this.formatter = f; }
    public void addAppender(LogAppender appender) { appenders.add(appender); }

    // ── THE CORE METHOD ──────────────────────────────────────────────
    // 1. Filter: is this message severe enough to log right now?
    // 2. Format: turn LogMessage into a String
    // 3. Fan-out: send the formatted string to EVERY registered appender
    public void log(LogLevel level, String text) {
        if (level.ordinal() < minLevel.ordinal()) {
            return;  // too verbose for current config — drop silently
        }

        LogMessage message = new LogMessage(level, text);
        String formatted = formatter.format(message);

        for (LogAppender appender : appenders) {
            appender.append(formatted);  // each appender writes independently
        }
    }

    // ── Convenience methods — what application code actually calls ──
    public void debug(String text) { log(LogLevel.DEBUG, text); }
    public void info(String text)  { log(LogLevel.INFO,  text); }
    public void warn(String text)  { log(LogLevel.WARN,  text); }
    public void error(String text) { log(LogLevel.ERROR, text); }
    public void fatal(String text) { log(LogLevel.FATAL, text); }
}
Main.java
Always demo — prove filtering + fan-out
public class Main {
    public static void main(String[] args) {

        Logger logger = Logger.getInstance();

        // Configure: log everything WARN and above, to BOTH console and file
        logger.setMinLevel(LogLevel.WARN);
        logger.addAppender(new ConsoleAppender());
        logger.addAppender(new FileAppender("app.log"));

        // DEBUG and INFO are below WARN — should be silently dropped
        logger.debug("This is a debug message");   // dropped
        logger.info("User logged in");            // dropped

        // WARN and above — printed to console AND written to app.log
        logger.warn("Disk space running low");    // shown
        logger.error("Failed to connect to DB");  // shown
        logger.fatal("Out of memory, shutting down"); // shown

        // Prove Singleton: same instance everywhere
        Logger sameLogger = Logger.getInstance();
        System.out.println("\nSame instance? " + (logger == sameLogger));
    }
}

/* Expected console output:
[WARN] 2026-06-13T10:15:30.123: Disk space running low
[ERROR] 2026-06-13T10:15:30.124: Failed to connect to DB
[FATAL] 2026-06-13T10:15:30.125: Out of memory, shutting down

Same instance? true

(app.log file will contain the same 3 lines)
*/
Why CopyOnWriteArrayList for appenders? Appenders are added rarely (at startup) but read on EVERY log call (potentially from many threads). CopyOnWriteArrayList optimizes for "read-heavy, write-rare" — no locking needed during iteration. Mention this if asked about concurrency.

SOLID Principles — where exactly in the code

This problem is the BEST showcase for SOLID because every class maps to exactly one principle in an obvious way. If an interviewer asks "explain SOLID with an example", this is the project to reference forever.
S
Single Responsibility
Every class has exactly one reason to change.
ConsoleAppender — only knows console I/O. FileAppender — only file I/O. SimpleLogFormatter — only formatting. Logger — only orchestration (filter + fan-out).
O
Open / Closed
Open for extension, closed for modification.
Add DatabaseAppender or RemoteAppender → new class implementing LogAppender + one addAppender() call. Logger.log() — zero changes.
L
Liskov Substitution
Any implementation can replace another without breaking callers.
Logger's for-loop calls appender.append(...) — works identically whether appender is ConsoleAppender, FileAppender, or any future appender. All are substitutable.
I
Interface Segregation
Don't force implementations to support unused methods.
LogAppender has exactly ONE method — append(). LogFormatter has exactly ONE — format(). No appender is forced to implement formatting logic, and vice versa — they're separate concerns, separate interfaces.
D
Dependency Inversion
High-level modules depend on abstractions, not concrete classes.
Logger (high-level orchestrator) holds List<LogAppender> and a LogFormatter — both interfaces. It never references ConsoleAppender, FileAppender, or SimpleLogFormatter by name in its logic. Concrete types are only chosen at configuration time in Main.
P

Design Patterns — what's used and why

1
Strategy Pattern (used TWICE — the core of this problem)
Used twice independently: (1) LogAppender — "where do logs go" is interchangeable behavior. (2) LogFormatter — "how logs look" is also interchangeable behavior. Keeping these as TWO separate Strategy interfaces (instead of one big config object) means each varies independently — you can change format without touching appenders and vice versa. Calling out that you used Strategy twice, for two different concerns, shows real understanding (not just pattern-name-dropping).
Used in: LogAppender + ConsoleAppender/FileAppender, and LogFormatter + SimpleLogFormatter
2
Singleton Pattern
There's exactly one logging configuration per application — one set of appenders, one minimum level. If every class created its own Logger instance, configurations (and log levels) could diverge across the app. Double-checked locking with volatile keeps it thread-safe.
Used in: Logger.getInstance()
3
Chain of Responsibility (mention as the "textbook alternative")
Classic Log4j-style design uses a CHAIN of level-handlers: a DebugHandler checks "is this DEBUG? handle it, then pass to next." then InfoHandler, etc. Each handler decides independently whether to process and/or forward. When to mention: if the interviewer asks "is there another way to structure level filtering?" — say: "Yes, Chain of Responsibility — each level has its own handler object, and they're linked in a chain. I chose the simpler ordinal-comparison approach because it's less code for the same effect at this scale, but CoR scales better if each level needs drastically different processing (not just a yes/no filter)."
Alternative design — not implemented, but name it if asked
4
Factory Pattern (extension — for per-class loggers)
If the interviewer asks "how would you support Log4j-style Logger.getLogger(MyClass.class) with different configs per class?" — say: "I'd add a LoggerFactory that maintains a Map<String, Logger> keyed by class/module name, creating a new configured Logger instance per key on first request (similar to the per-client pattern in a rate limiter)."
Extension point: LoggerFactory.getLogger(String name)
LoggerFactory.java — bonus answer for per-module loggers
Factory Pattern
// ── Design Pattern: FACTORY ───────────────────────────────────────────────
// Returns a named logger, creating it on first request (lazy init).
// Each module gets its own logger — e.g. could have its own minLevel.

import java.util.*;
import java.util.concurrent.*;

public class LoggerFactory {
    private static final Map<String, Logger> loggers = new ConcurrentHashMap<>();

    public static Logger getLogger(String name) {
        return loggers.computeIfAbsent(name, n -> Logger.getInstance());
        // In a fuller design, Logger constructor would no longer be a strict
        // singleton — each "name" could map to its own configured instance.
    }
}
// Usage: Logger log = LoggerFactory.getLogger("PaymentService");

Interview Tips — what separates good from great

Things to DO
✓Get the enum ORDER right — DEBUG to FATAL, ascending severity
✓Use ordinal() comparison for level filtering — clean one-liner
✓Keep Appender and Formatter as SEPARATE Strategy interfaces
✓Demo with multiple appenders active at once (console + file)
✓Mention Chain of Responsibility as the "textbook" alternative
✓Use try-with-resources for file I/O — shows Java fluency
Things to AVOID
✗Hardcoding if/else chains for level checks instead of ordinal()
✗Single appender field instead of a List (breaks "log to both")
✗Mixing formatting logic INTO each appender (duplication)
✗Forgetting append mode on FileWriter (overwrites old logs)
✗Not closing file resources (resource leak)
✗Saying "Singleton" but writing a public constructor
Bonus questions to prepare for:
"How would you make this asynchronous so logging doesn't block the main thread?" → Logger.log() pushes LogMessage onto a BlockingQueue; a separate background thread (or thread pool) consumes from the queue and calls appenders. This decouples "producing" logs from "writing" them.
"How would you add log rotation (new file per day, max file size)?" → RollingFileAppender — wraps FileAppender, checks file size/date before each write, and renames/rotates the file when exceeded. Same LogAppender interface — no changes elsewhere.
"What if different appenders need different minimum levels?" → Move minLevel from Logger into each Appender (each appender has its own threshold) — Logger always formats and passes the message; each appender decides whether to write it.
"How does this relate to Chain of Responsibility?" → CoR would model each level as a handler object with a "next" pointer; the request travels down the chain until a handler processes it. Our ordinal-comparison approach achieves the same filtering with less structure — appropriate when there's no per-level custom behavior beyond "log or don't".
"Thread safety — what if 100 threads call logger.info() simultaneously?" → CopyOnWriteArrayList for appenders (safe iteration), and each Appender's append() should itself be thread-safe (e.g. synchronized file writes, or a per-appender queue).
