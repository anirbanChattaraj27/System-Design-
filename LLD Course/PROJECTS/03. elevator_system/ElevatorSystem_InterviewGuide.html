Understanding the problem in depth — first

What is an Elevator System, really? A building has N elevators and M floors. People press buttons (either "I'm on floor 3, going up" from a floor panel, or "take me to floor 7" from inside the elevator). The system must: (1) decide WHICH elevator should serve each request, and (2) decide, for each elevator, WHAT TO DO NEXT — move up, move down, stop and open doors, or idle.
Why this is the HARDEST classic LLD question: It has TWO separate hard problems bundled together — (1) a state machine per elevator (idle/moving/door-open), and (2) a scheduling/dispatch algorithm (which of N elevators answers this call?). Most candidates run out of time trying to do both perfectly. The trick is to SCOPE DOWN early — say "I'll implement a simple state machine and a 'nearest idle elevator' strategy, and discuss more advanced scheduling (like SCAN/LOOK) verbally if time allows."

The 2 hard sub-problems — name both upfront, then pick simple versions of each:

Per-elevator state machine State Pattern (or enum)
An elevator is IDLE, MOVING_UP, MOVING_DOWN, or DOORS_OPEN at any time. Transitions depend on pending requests. We'll model this with an enum + a step() method — full State Pattern (separate classes per state) is mentioned as an extension.
Dispatch algorithm Strategy — "nearest elevator"
When a request comes in (floor 5, going UP), which of N elevators should respond? Simplest: pick the elevator with minimum |currentFloor - requestFloor| that's idle or moving toward it. We implement this; mention SCAN/LOOK as advanced alternatives.
Request queue per elevator Two heaps
Each elevator keeps an "upRequests" min-heap and "downRequests" max-heap — classic LeetCode-style elevator scheduling. Ensures requests are served in floor order, not arrival order (avoids unnecessary direction changes).
Observer for displays Mention only
Floor displays and direction indicators "observe" the elevator and update when its floor/state changes. Good bonus answer for "how would you update the UI?"
The approach we'll build: ElevatorController (Singleton) holds a list of Elevator objects. Each Elevator has a state (enum), current floor, direction, and two priority queues (up/down requests). A NearestElevatorStrategy (Strategy pattern) picks which elevator handles an external request. A simple step() method simulates movement one floor at a time — this is what we'll demo.

Phase 2 — Identify Entities & Quick Diagram

10 – 20 min
Two-layer thinking: Layer 1 = ONE elevator's behavior (state + its own request queue). Layer 2 = the CONTROLLER that owns multiple elevators and dispatches requests to them. Design layer 1 first — it's self-contained and easier — then layer 2 becomes "just" a router.
Step 1 — Identify the "varies vs fixed" split (2 min, say out loud)
Say: "An elevator's STATE varies over time (idle → moving → door open → idle), so that's either an enum with transition logic, or full State pattern. The DISPATCH ALGORITHM varies by requirement (nearest vs SCAN), so that's a Strategy. The CONTROLLER is fixed — one per building, so Singleton."
Step 2 — List the classes (2 min)
— Direction (enum) — UP, DOWN, IDLE
— ElevatorState (enum) — IDLE, MOVING, DOORS_OPEN
— Request — data holder: sourceFloor, destinationFloor (optional), direction

— DispatchStrategy (interface) — the Strategy: selectElevator(elevators, request)
— NearestElevatorStrategy — implementation
— ElevatorController — Singleton; owns elevators + strategy

// Direction the elevator is currently travelling (or IDLE = not moving)
public enum Direction { UP, DOWN, IDLE }

// ── State Pattern (lightweight version) ───────────────────────────────────
// Full State Pattern would make each of these a CLASS with its own
// behavior (IdleState.handle(), MovingState.handle()...).
// For an interview, an enum + a switch/if in Elevator.step() is the
// pragmatic choice — explain you'd extract to full State classes if
// each state's logic grew complex (e.g. maintenance mode, emergency stop).
public enum ElevatorState {
    IDLE,         // no pending requests, doors closed, not moving
    MOVING,       // travelling toward next stop
    DOORS_OPEN    // stopped at a floor, doors open
}

Elevator.java
SRP — core state machineState (lightweight)
import java.util.*;

// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Elevator manages ONLY its own movement, state, and request queues.
// It does NOT know about other elevators or how it was chosen — that's
// the Controller's job. This separation is what makes the class testable
// in isolation (you can unit-test ONE elevator with no controller at all).
//
// ── DATA STRUCTURE CHOICE: two priority queues ────────────────────────────
// upRequests   = min-heap → always serve the LOWEST floor above us next
// downRequests = max-heap → always serve the HIGHEST floor below us next
// This is the classic "elevator scheduling" trick: it guarantees we serve
// requests in floor-order along our current direction, never zig-zagging.

public class Elevator {

    private final int id;
    private int currentFloor;
    private ElevatorState state;
    private Direction direction;

    private final PriorityQueue<Integer> upRequests;   // min-heap (natural order)
    private final PriorityQueue<Integer> downRequests; // max-heap (reverse order)

    public Elevator(int id) {
        this.id           = id;
        this.currentFloor = 0;            // ground floor
        this.state        = ElevatorState.IDLE;
        this.direction    = Direction.IDLE;
        this.upRequests   = new PriorityQueue<>();                          // ascending
        this.downRequests = new PriorityQueue<>(Collections.reverseOrder()); // descending
    }

    // ── Add a destination floor (called for BOTH internal cabin requests
    // AND external requests once this elevator has been chosen) ──────
    public void addRequest(int floor) {
        if (floor > currentFloor) {
            upRequests.add(floor);
        } else if (floor < currentFloor) {
            downRequests.add(floor);
        }
        // floor == currentFloor → already here, nothing to queue

        // If we were idle, pick a direction now based on the new request
        if (state == ElevatorState.IDLE) {
            direction = (floor > currentFloor) ? Direction.UP
                       : (floor < currentFloor) ? Direction.DOWN
                       : Direction.IDLE;
            state = (direction == Direction.IDLE) ? ElevatorState.DOORS_OPEN : ElevatorState.MOVING;
        }
    }

    // ── THE SIMULATION TICK ───────────────────────────────────────────
    // Moves the elevator ONE floor per call (or opens/closes doors).
    // In a real system, this would be driven by a timer/motor controller —
    // for the interview, calling step() repeatedly in Main simulates time.
    public void step() {
        switch (state) {
            case IDLE:
                // nothing to do
                break;

            case DOORS_OPEN:
                // doors close, decide what's next
                state = ElevatorState.MOVING;
                decideNextDirection();
                break;

            case MOVING:
                if (direction == Direction.UP) {
                    currentFloor++;
                    if (!upRequests.isEmpty() && upRequests.peek() == currentFloor) {
                        upRequests.poll();              // arrived — remove this stop
                        state = ElevatorState.DOORS_OPEN;
                    }
                } else if (direction == Direction.DOWN) {
                    currentFloor--;
                    if (!downRequests.isEmpty() && downRequests.peek() == currentFloor) {
                        downRequests.poll();
                        state = ElevatorState.DOORS_OPEN;
                    }
                }
                break;
        }
    }

    // After doors close, decide: continue same direction, switch, or go idle
    private void decideNextDirection() {
        if (direction == Direction.UP && !upRequests.isEmpty()) {
            return; // keep going up — more stops above
        }
        if (direction == Direction.DOWN && !downRequests.isEmpty()) {
            return; // keep going down — more stops below
        }
        // No more requests in current direction — try the other direction
        if (!upRequests.isEmpty()) {
            direction = Direction.UP;
        } else if (!downRequests.isEmpty()) {
            direction = Direction.DOWN;
        } else {
            direction = Direction.IDLE;
            state     = ElevatorState.IDLE;
        }
    }

    // ── Helper for dispatch strategy: how "good" a fit is this elevator? ──
    // Simple metric: absolute floor distance. Lower = better.
    public int distanceTo(int floor) {
        return Math.abs(this.currentFloor - floor);
    }

    public int getId()            { return id; }
    public int getCurrentFloor() { return currentFloor; }
    public ElevatorState getState()     { return state; }
    public Direction getDirection()   { return direction; }
}
DispatchStrategy.java + NearestElevatorStrategy.java
Strategy PatternOCP + DIP
import java.util.*;

// ── Design Pattern: STRATEGY ──────────────────────────────────────────────
// "Which elevator answers this call?" is THE classic example of varying
// behavior. Real systems use complex heuristics (load balancing, zoning,
// SCAN/LOOK algorithms); we implement the simplest correct one and make
// it swappable.
// ── SOLID: Open/Closed ────────────────────────────────────────────────────
// Add ZoningStrategy or LoadBalancedStrategy later → new class implementing
// this interface. ElevatorController is untouched.

public interface DispatchStrategy {
    Elevator selectElevator(List<Elevator> elevators, Request request);
}

// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Does ONE thing: picks the elevator with the smallest floor distance
// to the request's floor. Doesn't care about direction matching —
// that nuance is exactly what a more advanced strategy would add.
public class NearestElevatorStrategy implements DispatchStrategy {
    @Override
    public Elevator selectElevator(List<Elevator> elevators, Request request) {
        Elevator best = null;
        int bestDistance = Integer.MAX_VALUE;

        for (Elevator e : elevators) {
            int dist = e.distanceTo(request.getFloor());
            if (dist < bestDistance) {
                bestDistance = dist;
                best = e;
            }
        }
        return best;  // elevators list is never empty in our design, so always non-null
    }
}
ElevatorController.java
Singleton + Strategy usageSRP + DIP
import java.util.*;

// ── Design Pattern: SINGLETON ─────────────────────────────────────────────
// One controller manages all elevators in the building — same reasoning
// as ParkingLot / RateLimiter / Logger. Two controllers would double-dispatch.
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Controller's ONE job: receive external requests, pick an elevator via
// the strategy, and forward the request. It does NOT implement movement —
// that's Elevator's job (separation of concerns).
// ── SOLID: Dependency Inversion ───────────────────────────────────────────
// Controller depends on DispatchStrategy (interface), never on
// NearestElevatorStrategy directly.

public class ElevatorController {

    private static volatile ElevatorController instance;

    private final List<Elevator> elevators;
    private DispatchStrategy dispatchStrategy;

    private ElevatorController(int numElevators) {
        this.elevators = new ArrayList<>();
        for (int i = 1; i <= numElevators; i++) {
            elevators.add(new Elevator(i));
        }
        this.dispatchStrategy = new NearestElevatorStrategy(); // sensible default
    }

    public static ElevatorController getInstance(int numElevators) {
        if (instance == null) {
            synchronized (ElevatorController.class) {
                if (instance == null) {
                    instance = new ElevatorController(numElevators);
                }
            }
        }
        return instance;
    }

    // Allows swapping strategy at runtime — e.g. switch to a
    // LoadBalancedStrategy during peak hours.
    public void setDispatchStrategy(DispatchStrategy strategy) {
        this.dispatchStrategy = strategy;
    }

    // ── EXTERNAL REQUEST: "I'm on floor X, going UP/DOWN" ────────────
    // 1. Ask the strategy which elevator should handle this
    // 2. Forward the floor to that elevator's queue
    public void requestElevator(int floor, Direction direction) {
        Request request = new Request(floor, direction);
        Elevator chosen = dispatchStrategy.selectElevator(elevators, request);
        chosen.addRequest(floor);
        System.out.printf("[DISPATCH] Floor %d (%s) -> Elevator %d%n",
            floor, direction, chosen.getId());
    }

    // ── INTERNAL REQUEST: "Take me to floor X" (from inside a cabin) ──
    // No dispatch needed — goes straight to the elevator you're already in.
    public void requestFloorFromInsideElevator(int elevatorId, int destinationFloor) {
        for (Elevator e : elevators) {
            if (e.getId() == elevatorId) {
                e.addRequest(destinationFloor);
                System.out.printf("[CABIN] Elevator %d -> Floor %d%n", elevatorId, destinationFloor);
                return;
            }
        }
    }

    // ── Advance simulation by one tick for ALL elevators ─────────────
    public void stepAll() {
        for (Elevator e : elevators) {
            e.step();
        }
    }

    public void printStatus() {
        for (Elevator e : elevators) {
            System.out.printf("  Elevator %d: floor=%d state=%s dir=%s%n",
                e.getId(), e.getCurrentFloor(), e.getState(), e.getDirection());
        }
    }
}
Main.java
Always demo — simulate ticks
public class Main {
    public static void main(String[] args) {

        // 3 elevators, all starting at ground floor (0)
        ElevatorController controller = ElevatorController.getInstance(3);

        // External request: someone on floor 5 wants to go UP
        controller.requestElevator(5, Direction.UP);

        // Internal request: person inside Elevator 1 wants floor 8
        controller.requestFloorFromInsideElevator(1, 8);

        System.out.println("\nInitial status:");
        controller.printStatus();

        // Simulate 6 time steps — watch Elevator 1 move toward floor 5, then 8
        for (int tick = 1; tick <= 6; tick++) {
            controller.stepAll();
            System.out.println("\nAfter tick " + tick + ":");
            controller.printStatus();
        }
    }
}

/* Expected output (abridged):
[DISPATCH] Floor 5 (UP) -> Elevator 1   (all elevators at floor 0, Elevator 1 picked — tie-break: first)
[CABIN] Elevator 1 -> Floor 8

Initial status:
  Elevator 1: floor=0 state=MOVING dir=UP
  Elevator 2: floor=0 state=IDLE dir=IDLE
  Elevator 3: floor=0 state=IDLE dir=IDLE

After tick 1:
  Elevator 1: floor=1 state=MOVING dir=UP
  ...
After tick 5:
  Elevator 1: floor=5 state=DOORS_OPEN dir=UP   (reached floor 5, doors open)
After tick 6:
  Elevator 1: floor=5 state=MOVING dir=UP       (doors closed, continuing to floor 8)
*/
Why "step by step" simulation instead of real threads/timers? In a 35-minute window, a deterministic step() method you call in a loop is MUCH easier to demo and reason about than real concurrency. If asked "how would this run in production?" — say: "Each Elevator would run on its own thread or be driven by a scheduled task calling step() every N milliseconds; the Controller's methods would need synchronization since multiple floor panels could call requestElevator() concurrently."

SOLID Principles — where exactly in the code

How to bring this up: The Elevator/Controller split is the cleanest SRP example across all 4 problems we've covered — "movement" and "dispatch" are TRULY independent concerns, and the code structure makes that obvious.
S
Single Responsibility
Every class has exactly one reason to change.
Elevator — only its own movement/state/queues. ElevatorController — only dispatch + aggregation. NearestElevatorStrategy — only the selection metric. Request — only data.
O
Open / Closed
Open for extension, closed for modification.
Add ZoningStrategy or SCANStrategy → new class implementing DispatchStrategy + one setDispatchStrategy() call. Elevator and ElevatorController's core logic — zero changes.
L
Liskov Substitution
Any implementation can replace another without breaking callers.
controller.requestElevator() calls dispatchStrategy.selectElevator(...) — works identically whether the strategy is NearestElevatorStrategy or any future strategy returning a valid Elevator.
I
Interface Segregation
Don't force implementations to support unused methods.
DispatchStrategy has exactly ONE method — selectElevator(). A strategy implementation isn't forced to also implement movement logic or state transitions — those stay in Elevator.
D
Dependency Inversion
High-level modules depend on abstractions, not concrete classes.
ElevatorController holds a DispatchStrategy field (interface) — never references NearestElevatorStrategy in its logic, only at construction/configuration time. This is why setDispatchStrategy() can swap algorithms at runtime without recompiling Controller.
P

Design Patterns — what's used and why

1
State Pattern (lightweight version)
An elevator's behavior fundamentally depends on its current state — what step() does differs completely for IDLE vs MOVING vs DOORS_OPEN. We implemented this as an enum + switch for speed, but it IS the State pattern's core idea: behavior varies by current state. If asked to go deeper: "I'd extract each case into its own class — IdleState, MovingState, DoorsOpenState — each implementing a common ElevatorStateHandler interface with a handle(Elevator) method. Elevator would hold a reference to its current state object and delegate step() to it. This helps when each state has MANY lines of distinct logic (e.g. adding emergency/maintenance states) — the switch statement would otherwise become huge and violate OCP."
Used in: ElevatorState enum + Elevator.step() switch. Full version: extension point.
2
Strategy Pattern (dispatch algorithm)
"Which elevator answers this call?" is the single most variable piece of an elevator system — entire research papers exist on elevator scheduling (SCAN, LOOK, destination dispatch, zoning). By isolating this behind DispatchStrategy, we can start with the simplest correct version (nearest elevator) and swap in smarter ones later without touching Elevator or Controller. This is also the answer to "the algorithm could get arbitrarily complex — how do you keep your design from becoming spaghetti?"
Used in: DispatchStrategy interface + NearestElevatorStrategy
3
Singleton Pattern
One controller manages the building's elevator bank — exactly the same reasoning as ParkingLot, RateLimiter, and Logger. Two independent controllers could dispatch conflicting instructions to the same elevator.
Used in: ElevatorController.getInstance()
4
Observer Pattern (extension — for displays/indicators)
If asked "how would you update floor displays and direction arrows in real time?" — say: "I'd make Elevator a subject that floor displays and in-cabin indicators observe. Whenever step() changes currentFloor or direction, Elevator notifies all registered observers, who update their UI. This decouples 'how the elevator moves' from 'how that movement is displayed' — adding a new display type requires zero changes to Elevator."
Extension point: ElevatorObserver interface + Elevator.notifyObservers()

// ── Design Pattern: OBSERVER ──────────────────────────────────────────────
// Displays/indicators register themselves and get notified on every change.
// Elevator doesn't know or care WHAT the observers do with the update.

public interface ElevatorObserver {

// Example concrete observer — a floor display panel
public class FloorDisplay implements ElevatorObserver {
    @Override
    public void onElevatorUpdate(int elevatorId, int currentFloor, Direction direction) {
        System.out.printf("[DISPLAY] Elevator %d is now at floor %d (%s)%n",
            elevatorId, currentFloor, direction);
    }
}

Interview Tips — what separates good from great

Things to DO
✓Scope down aggressively in the first 10 minutes
✓Separate "one elevator's behavior" from "the dispatcher"
✓Use two priority queues (up/down) — the classic correct structure
✓Implement a simple step() — easy to demo deterministically
✓Distinguish external (dispatch) vs internal (direct) requests
✓Mention State pattern, Observer, SCAN — even if not coded
Things to AVOID
✗Trying to implement SCAN/LOOK scheduling in 35 minutes
✗Using a single ArrayList of requests (loses floor-order guarantee)
✗Real threads/Thread.sleep() for "movement" — overcomplicates demo
✗Putting dispatch logic inside the Elevator class itself
✗Forgetting to handle "elevator finishes all requests → IDLE"
✗Ignoring direction when picking "nearest" (fine to mention as limitation)
Bonus questions to prepare for:
"Your nearest-elevator strategy ignores direction — is that a problem?" → Yes: an elevator moving DOWN past floor 5 shouldn't be picked for an UP request at floor 5 even if it's "nearest" at that instant. A better strategy checks direction compatibility, or only considers IDLE elevators + elevators already moving toward the request in the same direction.
"How would you implement SCAN/LOOK scheduling?" → Each elevator services all requests in its current direction until none remain, then reverses — which is EXACTLY what our two-heap + decideNextDirection() already does per elevator! SCAN at the building level would extend this to coordinating multiple elevators into "zones" so they don't cluster.
"How do you prevent starvation — a request on floor 10 waiting forever if elevators keep getting closer requests?" → Add a max-wait timer per request; if exceeded, temporarily boost its priority or force the nearest idle elevator to serve it next.
"What about capacity (max weight/people)?" → Add a capacity field and currentLoad to Elevator; DispatchStrategy.selectElevator() filters out elevators at capacity before computing distance.
"How would you make this thread-safe for concurrent requests?" → synchronized on requestElevator() and addRequest(), or use a single-threaded executor per elevator that processes its queue, with the controller submitting tasks to the right executor.
