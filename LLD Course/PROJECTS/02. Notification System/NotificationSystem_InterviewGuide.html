Understanding the problem in depth — first

What is a Notification System, really? When something happens in your app — a new order, a password reset, a promotional campaign — the system needs to tell certain users about it, through one or more channels (Email, SMS, Push, WhatsApp). The system decides: WHICH users to notify, through WHICH channels, with WHAT message content.
Why this question is uniquely rich for SDE-1: It's the only classic LLD problem where THREE of the most important patterns appear naturally and necessarily — Observer (who gets notified?), Strategy (how is the notification sent?), and Factory (who creates the right sender?). Each pattern solves a genuinely different problem in the same system — making this the best problem to demonstrate pattern fluency.

The 3 axes of variation — identify these first, each becomes a pattern:

WHO gets notified Observer Pattern
Users subscribe to event types (ORDER_PLACED, PROMO, ALERT). When an event fires, all subscribers to that type get notified. Adding/removing subscribers doesn't change the event source.
HOW it's delivered Strategy Pattern
Email, SMS, Push notification, WhatsApp. Each channel has a completely different implementation. Must be pluggable — a new channel = new class, no changes elsewhere.
WHICH channel to create Factory Pattern
Based on user preferences or notification type, a factory decides which NotificationSender to instantiate. Callers don't write "new EmailSender()" — they ask the factory.
User preferences User Profile
Each user has preferred channels (some want Email only, some want SMS + Push). The system respects these preferences — one event may send via 2 channels for one user and 1 channel for another.
The exact system we'll build: A NotificationService (Singleton) accepts events. Users subscribe to event types (Observer). When an event fires, all subscribers are notified. For each subscriber, the system checks their preferred channels, uses a NotificationSenderFactory to get the right NotificationSender (Strategy), and sends. Every piece is independently extensible.

// Carries notification data ONLY. No sending logic, no routing logic.
// Immutable — once created, a notification's content never changes.

public class Notification {
    private final NotificationType type;
    private final String title;
    private final String message;

    public Notification(NotificationType type, String title, String message) {
        this.type    = type;
        this.title   = title;
        this.message = message;

    public NotificationType getType()    { return type; }
    public String getTitle()             { return title; }
    public String getMessage()           { return message; }

User.java
SRP — user data + channel prefs
import java.util.*;

// ── SOLID: Single Responsibility ──────────────────────────────────────────
// User knows about itself — contact info and channel preferences.
// It does NOT decide when or how to send — that's NotificationService's job.
// ── Key design point: preferredChannels is a List, not a single Channel ───
// Because a user can say "I want BOTH Email AND SMS for order updates".

public class User {
    private final String userId;
    private final String name;
    private final String email;
    private final String phone;
    private final String deviceToken;          // for push notifications
    private final List<Channel> preferredChannels;

    public User(String userId, String name, String email,
                String phone, String deviceToken, List<Channel> preferredChannels) {
        this.userId            = userId;
        this.name              = name;
        this.email             = email;
        this.phone             = phone;
        this.deviceToken       = deviceToken;
        this.preferredChannels = preferredChannels;
    }

    public String getUserId()               { return userId; }
    public String getName()                 { return name; }
    public String getEmail()                { return email; }
    public String getPhone()                { return phone; }
    public String getDeviceToken()          { return deviceToken; }
    public List<Channel> getPreferredChannels() { return preferredChannels; }
}
NotificationSender.java + EmailSender + SmsSender + PushSender
Strategy Pattern — the HOW axisSRP + ISP + OCP
// ── Design Pattern: STRATEGY ──────────────────────────────────────────────
// "How is the notification delivered?" varies by channel.
// Each implementation encapsulates one delivery mechanism completely.
// ── SOLID: Interface Segregation ──────────────────────────────────────────
// One method only — send(). No sender is forced to implement channel-specific
// methods it doesn't need (e.g. EmailSender doesn't implement getDeviceToken()).
// ── SOLID: Open/Closed ────────────────────────────────────────────────────
// Add WhatsAppSender → new class implementing this interface + factory case.
// NotificationService.notify() — ZERO changes.

public interface NotificationSender {
    void send(User user, Notification notification);
}

// ── SOLID: SRP — EmailSender knows ONLY about email delivery ──────────────
public class EmailSender implements NotificationSender {
    @Override
    public void send(User user, Notification notification) {
        // In production: integrate with SMTP / SendGrid / SES
        System.out.printf("[EMAIL]  To: %s | Subject: %s | Body: %s%n",
            user.getEmail(), notification.getTitle(), notification.getMessage());
    }
}

// ── SOLID: SRP — SmsSender knows ONLY about SMS delivery ──────────────────
public class SmsSender implements NotificationSender {
    @Override
    public void send(User user, Notification notification) {
        // In production: integrate with Twilio / AWS SNS
        System.out.printf("[SMS]    To: %s | %s: %s%n",
            user.getPhone(), notification.getTitle(), notification.getMessage());
    }
}

// ── SOLID: SRP — PushSender knows ONLY about push notification delivery ───
public class PushSender implements NotificationSender {
    @Override
    public void send(User user, Notification notification) {
        // In production: integrate with FCM (Firebase Cloud Messaging)
        System.out.printf("[PUSH]   To device: %s | %s: %s%n",
            user.getDeviceToken(), notification.getTitle(), notification.getMessage());
    }
}
NotificationSenderFactory.java
Factory Pattern — the WHICH axisSRP + OCP + DIP
// ── Design Pattern: FACTORY ───────────────────────────────────────────────
// The NotificationService says "I need a sender for EMAIL" — it doesn't
// say "new EmailSender()". The Factory encapsulates the creation decision.
// WHY both Strategy AND Factory? Strategy defines the CONTRACT (interface).
// Factory handles CREATION (instantiation). Different responsibilities.
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// Factory's one job: map a Channel enum to the right NotificationSender.
// ── SOLID: Open/Closed ────────────────────────────────────────────────────
// Add WHATSAPP: add "case WHATSAPP: return new WhatsAppSender()". Done.
// ── SOLID: Dependency Inversion ───────────────────────────────────────────
// Returns NotificationSender (interface), never a concrete type to callers.

public class NotificationSenderFactory {
    public static NotificationSender getSender(Channel channel) {
        switch (channel) {
            case EMAIL: return new EmailSender();
            case SMS:   return new SmsSender();
            case PUSH:  return new PushSender();
            default: throw new IllegalArgumentException("Unknown channel: " + channel);
        }
    }
}
NotificationService.java
Observer Subject + SingletonSRP + DIP
import java.util.*;

// ── Design Pattern: OBSERVER ──────────────────────────────────────────────
// NotificationService IS the "Subject" in Observer pattern.
// Users are the "Observers" — they register interest in specific event types.
// When an event fires, the subject notifies ALL registered observers for
// that type. The event source doesn't know anything about its subscribers.
// ── Design Pattern: SINGLETON ─────────────────────────────────────────────
// One global service manages all subscriptions across the app.
// ── SOLID: Single Responsibility ──────────────────────────────────────────
// NotificationService manages subscriptions and routes notifications.
// It does NOT know HOW to send — it delegates to Factory + Senders.
// ── SOLID: Dependency Inversion ───────────────────────────────────────────
// Calls NotificationSender (interface) — never a concrete sender directly.

public class NotificationService {

    private static volatile NotificationService instance;

    // Observer registry: NotificationType → List of subscribed Users
    private final Map<NotificationType, List<User>> subscribers;

    private NotificationService() {
        subscribers = new HashMap<>();
    }

    public static NotificationService getInstance() {
        if (instance == null) {
            synchronized (NotificationService.class) {
                if (instance == null) {
                    instance = new NotificationService();
                }
            }
        }
        return instance;
    }

    // ── OBSERVER: subscribe ──────────────────────────────────────────
    // User says: "I want to receive ORDER_PLACED notifications."
    public void subscribe(NotificationType type, User user) {
        subscribers
            .computeIfAbsent(type, t -> new ArrayList<>())
            .add(user);
        System.out.printf("[SUBSCRIBE] %s subscribed to %s%n", user.getName(), type);
    }

    // ── OBSERVER: unsubscribe ────────────────────────────────────────
    public void unsubscribe(NotificationType type, User user) {
        List<User> list = subscribers.get(type);
        if (list != null) list.remove(user);
        System.out.printf("[UNSUBSCRIBE] %s unsubscribed from %s%n", user.getName(), type);
    }

    // ── OBSERVER: notify (the core fan-out method) ────────────────────
    // 1. Find all users subscribed to this notification's type
    // 2. For each user, loop through their preferred channels
    // 3. Ask Factory for the right sender per channel
    // 4. Delegate the actual sending to that sender (Strategy)
    public void notify(Notification notification) {
        List<User> targets = subscribers.getOrDefault(
            notification.getType(), Collections.emptyList());

        if (targets.isEmpty()) {
            System.out.println("[NOTIFY] No subscribers for: " + notification.getType());
            return;
        }

        System.out.printf("%n[NOTIFY] Sending '%s' to %d subscriber(s)...%n",
            notification.getTitle(), targets.size());

        for (User user : targets) {
            for (Channel channel : user.getPreferredChannels()) {
                // Factory picks the right Strategy implementation
                NotificationSender sender = NotificationSenderFactory.getSender(channel);
                sender.send(user, notification);  // Strategy executes
            }
        }
    }
}

Demo — prove Observer fan-out + per-user channel prefs
import java.util.*;

public class Main {
    public static void main(String[] args) {

        NotificationService service = NotificationService.getInstance();

        // User 1: wants Email + SMS for orders, Email for promos
        User alice = new User("u1", "Alice", "alice@mail.com", "+91-9999", "dev-token-A",
            Arrays.asList(Channel.EMAIL, Channel.SMS));

        // User 2: wants only Push for orders
        User bob = new User("u2", "Bob", "bob@mail.com", "+91-8888", "dev-token-B",
            Arrays.asList(Channel.PUSH));

        // Subscribe both to ORDER_PLACED; only Alice to PROMO
        service.subscribe(NotificationType.ORDER_PLACED, alice);
        service.subscribe(NotificationType.ORDER_PLACED, bob);
        service.subscribe(NotificationType.PROMO, alice);

        // Fire an ORDER_PLACED event — both users notified, different channels
        service.notify(new Notification(
            NotificationType.ORDER_PLACED,
            "Order Confirmed!",
            "Your order #1234 has been placed."));

        // Fire a PROMO event — only Alice gets it
        service.notify(new Notification(
            NotificationType.PROMO,
            "50% Off Today!",
            "Use code SAVE50 at checkout."));

        // Bob unsubscribes from ORDER_PLACED
        service.unsubscribe(NotificationType.ORDER_PLACED, bob);

        // Fire another order — only Alice gets it now
        service.notify(new Notification(
            NotificationType.ORDER_PLACED,
            "Order Shipped!",
            "Your order #1234 is on the way."));
    }
}

SOLID Principles — where exactly in the code

This problem shows SOLID most clearly across multiple patterns. Each principle maps to a specific design decision — not just a class. The Dependency Inversion principle in particular is visible in THREE places simultaneously.
S
Single Responsibility
Every class has exactly one reason to change.
EmailSender — only email I/O. SmsSender — only SMS I/O. Notification — only data. NotificationSenderFactory — only object creation. NotificationService — only routing/subscription management.
O
Open / Closed
Open for extension, closed for modification.
Add WhatsApp channel: new Channel.WHATSAPP enum value + WhatsAppSender class + one factory case. NotificationService.notify() — zero changes. Add new NotificationType: one enum value. Zero changes elsewhere.
L
Liskov Substitution
Any implementation can replace another without breaking callers.
sender.send(user, notification) in NotificationService works identically whether sender is EmailSender, SmsSender, or any future WhatsAppSender — all are substitutable without the service knowing the difference.
I
Interface Segregation
Don't force implementations to support unused methods.
NotificationSender has exactly ONE method — send(). EmailSender is not forced to implement getDeviceToken() for push, SmsSender is not forced to implement SMTP logic. Each knows only what it needs.
D
Dependency Inversion
High-level modules depend on abstractions, not concrete classes.
NotificationService (high-level) holds Map<NotificationType, List<User>> and calls NotificationSender (interface) — never Email/SMS/PushSender directly. NotificationSenderFactory returns NotificationSender (interface) — callers don't see concrete types. This is DIP in THREE layers at once.
P

Design Patterns — what's used, why, and the key distinction

The most important thing to say in this problem: "I'm using Strategy AND Factory together, and they solve DIFFERENT problems — Strategy defines the interface (the contract for HOW to send), Factory handles object creation (the WHICH to instantiate). They're complementary, not redundant." This distinction alone separates good SDE-1 answers from great ones.
1
Observer Pattern — the WHO axis
Users (observers) register interest in specific event types (subjects). When an event fires, the subject fans out to all registered observers — without the event source knowing who they are. This decoupling is the entire point: a new order service can fire ORDER_PLACED without knowing anything about who subscribed or how many they are. Adding a new observer (e.g. an audit logger) requires zero changes to any existing code — just a subscribe() call.
Used in: NotificationService (subject) + User (observer) + subscribe/unsubscribe/notify
2
Strategy Pattern — the HOW axis
Email, SMS, and Push are three completely different delivery mechanisms — different APIs, different libraries, different failure modes. By defining NotificationSender as an interface, each mechanism is encapsulated independently. NotificationService doesn't care HOW Email is sent (SMTP? SendGrid? SES?) — it just calls send(). Swapping SendGrid for SES means changing only EmailSender — nothing else.
Used in: NotificationSender interface + EmailSender, SmsSender, PushSender
3
Factory Pattern — the WHICH axis
NotificationService shouldn't write new EmailSender() — that couples it to the concrete type. If EmailSender's constructor changes (e.g. needs an API key injected), every caller breaks. The Factory centralises this decision: "given Channel.EMAIL, create the right sender". One change in the factory fixes everything. Also note: the Factory returns the NotificationSender interface — callers never see the concrete type (DIP applied).
Used in: NotificationSenderFactory.getSender(Channel)
4
Singleton Pattern
One global subscription registry. If two parts of the app got different NotificationService instances, a subscribe() in one wouldn't be visible in the other — a user who subscribed would miss notifications. Same reasoning as every other Singleton in our series.
Used in: NotificationService.getInstance()
RetryNotificationSender.java — bonus: Decorator Pattern
Decorator Pattern
// ── Design Pattern: DECORATOR ─────────────────────────────────────────────
// Wraps any NotificationSender and adds retry logic — without modifying
// EmailSender, SmsSender, or any existing implementation.
// If asked "how would you add retry on failure?" — this is the answer.
// OCP: existing senders are closed for modification, open for wrapping.

public class RetryNotificationSender implements NotificationSender {
    private final NotificationSender delegate;
    private final int maxRetries;

    public RetryNotificationSender(NotificationSender delegate, int maxRetries) {
        this.delegate   = delegate;
        this.maxRetries = maxRetries;
    }

    @Override
    public void send(User user, Notification notification) {
        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            try {
                delegate.send(user, notification);
                return;  // success — stop retrying
            } catch (Exception e) {
                System.out.printf("[RETRY] Attempt %d failed: %s%n", attempt, e.getMessage());
                if (attempt == maxRetries) throw e;
            }
        }
    }
}
// Usage in factory: return new RetryNotificationSender(new EmailSender(), 3);

Interview Tips — what separates good from great

Things to DO
✓Name all 3 patterns in your requirements summary
✓Explain WHY Strategy + Factory are both needed (different jobs)
✓Model preferredChannels as a List on User — not a single value
✓Demo with 2 users + different channels — proves fan-out works
✓Show unsubscribe working — proves Observer completeness
✓Mention Decorator (retry) as bonus when asked about resilience
Things to AVOID
✗Using a single Channel field instead of List<Channel> on User
✗Putting send logic inside NotificationService (violates SRP)
✗Writing new EmailSender() inside NotificationService (skip Factory)
✗Giant if/else chain for channels inside a single send method
✗Confusing Observer (who) with Strategy (how) — keep them separate
✗Forgetting unsubscribe — interviewers always check it's there
Bonus questions to prepare for:
"How would you add retry on failure?" → Decorator pattern wrapping any NotificationSender — shown in code above. New behaviour without touching existing classes.
"How would you make sends asynchronous?" → NotificationService.notify() pushes Notification + User pairs onto a BlockingQueue; a thread pool consumes from the queue and calls sender.send(). The Observer fan-out still happens synchronously (finding subscribers), only the actual sending is async.
"How would you handle user preferences changing at runtime?" → User.preferredChannels would be mutable (or User becomes a mutable entity with setPreferredChannels()); no changes needed to NotificationService — it reads preferences at notification time, not at subscribe time.
"What if EmailSender is slow and blocks others?" → Per-channel thread pool: one executor for Email, one for SMS, one for Push. Each sender submits to its own executor so a slow email doesn't delay an SMS.
"How would you add notification templates per channel?" → Add a NotificationFormatter interface (another Strategy) — EmailFormatter returns HTML, SmsFormatter returns short text. Each Sender gets a Formatter injected at construction via Factory.
